
# ColliderOpsAI Model Card

## Model Overview

ColliderOpsAI currently uses baseline machine learning models to classify collider-style event records as either `signal` or `background`.

The model is part of a larger AI-assisted research workbench that supports event classification, confidence-based triage, batch prediction, and future RAG/agentic research assistance.

This model card documents the current model behavior, intended use, input features, output format, limitations, and future improvement plan.

---

## Current Production Model

The current default model used by the FastAPI inference service is:

```text
random_forest_baseline.joblib
```

Model metadata exposed by the API:

```text
model_name: random_forest_baseline
model_version: v1
```

The model is loaded by:

```text
app/model_loader.py
```

Predictions are generated by:

```text
app/predict.py
```

---

## Model Type

Current model:

```text
Random Forest Classifier
```

Baseline model also trained:

```text
Logistic Regression
```

The Random Forest model is used as the default inference model because it provides a stronger non-linear baseline for structured/tabular data compared with a simple linear model.

---

## Task

The model performs binary classification.

Target classes:

```text
signal
background
```

The current task is to classify collider-style event records into one of these two categories based on numerical event-level features.

---

## Intended Use

The model is intended for:

- Demonstrating an end-to-end ML inference workflow for scientific-style tabular data
- Supporting event-level classification in the ColliderOpsAI research workbench
- Producing prediction probabilities for confidence-based triage
- Supporting batch analysis workflows
- Providing a foundation for future model explainability and research-assistant capabilities

---

## Not Intended For

The current model should not be used for:

- Real scientific discovery
- Production-grade particle physics analysis
- Replacing specialized CERN analysis frameworks
- Making claims about actual Higgs/event discovery
- High-stakes scientific conclusions

The current dataset is small and synthetic/fallback-style, so model performance should be treated as pipeline validation rather than meaningful scientific accuracy.

## Output Schema

The model-serving API returns:

```json
{
  "prediction": "signal",
  "probability": 0.91,
  "model_name": "random_forest_baseline",
  "model_version": "v1",
  "risk_level": "high_confidence",
  "needs_review": false
}
```

Output fields:

| Field | Description |
|---|---|
| `prediction` | Predicted class: `signal` or `background` |
| `probability` | Highest class probability returned by the model |
| `model_name` | Name of the model used for inference |
| `model_version` | Current model version |
| `risk_level` | Confidence category based on probability threshold |
| `needs_review` | Boolean flag indicating whether the prediction should be reviewed |

---

## Confidence Triage

ColliderOpsAI uses prediction probability to support triage.

Current default threshold:

```text
0.75
```

Triage rules:

```text
probability >= 0.75 → high_confidence, needs_review = false
probability < 0.75  → low_confidence, needs_review = true
probability missing → unknown, needs_review = true
```

This turns the model output into a practical research workflow by helping users identify uncertain events that may require expert review.

## Training Data

The current MVP uses a small fallback collider-style dataset generated locally by:

```text
etl/download_cern_data.py
```

Current raw data location:

```text
data/raw/collider_events.csv
```

Important limitation:

The current dataset is intentionally small and is used to validate the end-to-end ML pipeline. It is not yet a large real CERN/LHC dataset.

---

## Feature Engineering

Feature preparation is handled by:

```text
training/feature_engineering.py
```

Current feature engineering steps:

- Load collider-style CSV data
- Select numerical feature columns
- Exclude identifier columns such as `event_id`
- Map labels to numeric targets
  - `background` → `0`
  - `signal` → `1`
- Split data into training and testing samples

---

## Training Pipeline

Model training is handled by:

```text
training/train.py
```

Current training flow:

```text
load dataset
→ split features and labels
→ train Logistic Regression baseline
→ train Random Forest baseline
→ save model artifacts with joblib
```

Saved model artifacts are stored under:

```text
models/
```

---

## Evaluation

Model evaluation is handled by:

```text
training/evaluate.py
```

Metrics tracked:

- Accuracy
- Precision
- Recall
- F1 score

Important note:

Because the current dataset is very small, evaluation scores may appear perfect or near-perfect. These scores should not be interpreted as meaningful scientific model performance. They only confirm that the pipeline is functioning end to end.

A more realistic evaluation will be added after integrating a larger collider-style dataset.

## Batch Prediction Behavior

The batch prediction endpoint accepts multiple events and returns:

- Row-level predictions
- Row-level probability
- Row-level confidence triage
- Batch-level summary statistics

Batch summary fields:

```text
total_events
signal_count
background_count
high_confidence_count
low_confidence_count
review_required_count
average_probability
```

This makes the model more useful for research-style workflows where users need to inspect a full experiment or batch run rather than a single record.

## Known Limitations

Current limitations:

- Dataset is small and not yet representative of real collider-scale data
- Model performance metrics are not yet scientifically meaningful
- No SHAP or feature-attribution explanation layer yet
- No MLflow model registry yet
- No automated model retraining pipeline yet
- No model drift monitoring yet
- No real CERN dataset integration yet
- No external validation against accepted physics benchmarks
